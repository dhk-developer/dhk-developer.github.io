What it is

Memora is a rhythm game I've been making on my own since late 2025. It's in the style of Phigros and Arcaea, where the lines you tap on move around the screen, with a visual-novel story attached. It runs on Android and is built in Unity 6 with C#.

I wanted to push the moving-line idea further. In Memora a note can sit on a line, float in open space, fly at another note, or aim at a point that is still moving when you hit it. Most of the screen is choreographed to the music. The clip at the top is one of my charts on autoplay.

The code is private, because I'd like to release the game one day. I've put architecture notes, diagrams and a small separate code sample in a public repository.

The first problem: what does the player actually hit?

Once lines move, it gets hard to say where and when a note should be judged. My early versions let the note's animation and its hit position share the same data. That meant every visual idea was also a gameplay change. An animation that overshot moved the hit point. Camera shake moved the target.

So I split every note into two parts that never write to each other:

  • Judgement data: the beat, what it's aimed at (a line, a point in space, another note) and the action (tap, hold, slide or flick). Input is only ever checked against this.
  • Presentation: how it enters, moves, scales, fades and leaves, written as keyframes in beats so it can follow the music.

The rule I stuck to is that nothing decorative can move a scoring target. Camera, layers and effects are applied after the hit position has been worked out. A nice side effect is "visual-only" notes, which look exactly like real notes but are never judged or scored, so I can use them for fake-outs.

It costs more data per note and two code paths to keep in step. In return, when a play says Miss, there is one place to look to find out why.

Timing

Frame time isn't precise enough for a rhythm game, and it drifts away from the audio. Memora takes its time from the audio system's DSP clock instead. Song time is the audio time since the song was scheduled to start, minus the chart's offset and the player's measured device latency. Every line position, target and animation is worked out fresh from that beat each frame, so a dropped frame can't knock anything off course.

Scoring adds up to exactly 1,000,000 for a perfect run: 900,000 for accuracy, where a Great is worth 70% of a Perfect, and 100,000 for combo.

Try the timing windows

A ring closes in on the circle once per beat at 100 BPM. Tap the circle, or press Space, as the ring meets it. Each tap is judged against the same windows Memora uses by default: ±100 ms for Perfect, ±250 ms for Great, anything else is a Miss.

This runs on the browser's audio clock, which is the same idea as the game: the beat comes from audio time, not from frame time. Browsers and Bluetooth headphones add their own delay, which is exactly what the calibration screen in Memora measures.

Phones and headphones all add their own delay, so there's a calibration screen. It plays a four-beat loop and asks for four taps. I take the mean of the middle two offsets so that one stray tap can't drag the result, and if the taps disagree too much it asks you to try again instead of saving a bad value. I wrote those rules down as plain sentences before writing any code, which is a habit from my BA work, and the code was straightforward after that.

Notes that aim at moving things

A floating note can be aimed at another note. The tricky part is choosing when to look at the target. If note B flies at note A, B has to arrive where A will be at B's hit time, not where A was at its own hit time.

To make that reliable, anything a note can aim at has to work out its position from only the chart, the beat and the screen size. It can't read the previous frame or anything stored while playing. That's what lets the editor jump backwards through a song and get the same result as playing forwards, and I have checks that seek backwards and compare.

Notes can approach in two ways. By default they aim at where the target will be when you hit it. The other mode follows the target as it moves, with a correction when a line jumps instantly so the note doesn't jump with it.

The charting editor

I write charts in a Unity editor window I built. It has a timeline, a live preview of the playfield, waveform and slowed-down playback, layers, a library of reusable patterns and undo.

Early on, the preview had its own simplified version of the gameplay maths, and the two drifted apart. The fix was to move that maths into shared code that both the game and the editor call, and to add checks comparing the two. I'd do that from day one next time.

Being able to jump to any beat instantly needed a few specific pieces:

  • an interval tree to find everything active at a given beat;
  • repeated events stored once and only expanded for the part of the song being looked at;
  • a cached running total to convert variable scroll speed into distance;
  • seek requests where the newest one wins, and the preview only shows a result once it's complete.

Finding a slowdown in the editor

On bigger charts, playback in the editor got sluggish. I profiled it before changing anything. One inspector panel was serialising the whole chart four times on every layout pass and four more times on every repaint, just to prepare undo snapshots when nothing had changed.

I changed that panel to record undo only when something is actually edited, cached results that were being recalculated several times per repaint, and stopped drawing timeline rows that were off screen. These are averages from the same sections of three charts before and after:

Reusable patterns

Charts repeat ideas, like a stream of notes or two lines trading a melody. I save these as presets with parameters. Applying one copies it into the chart as ordinary notes with fresh IDs, as a single undo step, and records which version of the preset it came from. If I later change the preset, finished charts stay as they are. I chose copies over live links because I never want a song to change without me deciding it should.

Not breaking old charts and saves

Every new feature is optional data, and old fields are kept readable even after something replaces them. Before saving, the editor checks for data the game can't handle yet, so nothing is silently dropped.

Story progress is saved with a checksum. It's written to a temporary file first and then swapped in, with a backup kept, so a crash halfway through a save can't corrupt it. A save from a newer version of the game is never overwritten by an older one.

What isn't finished

  • Songs with tempo changes aren't supported yet. Doing it properly means one clock that playback, the grid, the waveform and judgement all agree on, and I'd rather leave it out than fake it.
  • Layers on playable notes are reserved in the data format but not connected.
  • I haven't done proper performance testing on a range of phones yet. The editor numbers above are measured; measuring on phones is the next job.

What I'd do differently

  • Split the project into separate assemblies early. Two classes grew very large, and splitting them into partial files made them easier to read but didn't reduce how tangled they are.
  • Write the shared gameplay maths first, before the editor preview, so they never drift.
  • Test on real phones sooner.

If you'd like to talk about any of this, the parts I enjoy explaining most are the audio clock, the moving targets and how I checked the editor fix didn't change anything.
